# Как разобраться в model registry

Начни с запуска из `README.md` и `examples/demo.py`. Для работы не нужны папки с чужой машины: demo создаёт небольшой JSON-файл с коэффициентами линейной модели и вычисляет метрику на синтетических данных. Обучение и оценка в этом примере происходят у клиента; сервер сохраняет переданные байты и сведения.

## Три понятия

**Модель** — карточка с именем и командой: например, `mlds_1 / linear-demo`. **Версия** — неизменяемая публикация этой модели: артефакт, параметры, метрики и сведения о происхождении. **Alias** — удобное имя, которое можно переназначить: сегодня `production` указывает на версию 1, завтра — на 2.

Две загрузки одинакового файла создают две версии. Registry хранит историю публикаций и не определяет, улучшилось ли качество. Указатель `production` не запускает модель и не подтверждает её готовность к эксплуатации.

## В каком порядке читать код

1. `registry/schemas.py`: какие JSON-данные клиент отправляет и получает; найди обязательные поля происхождения.
2. `registry/schema.sql`: три таблицы, первичные и внешние ключи; сравни их с ER-диаграммой в отчёте.
3. `registry/storage.py`: запись файла, ограничение размера, SHA256 и выдача артефакта.
4. `registry/db.py`: обычные SQL-запросы, транзакция создания версии и работа с aliases.
5. `registry/app.py`: как HTTP-запрос соединяет валидацию, SQL и файловые операции.
6. `examples/demo.py` и тесты: полный пользовательский сценарий и ожидаемое поведение при ошибках.

ORM отсутствует намеренно: Python передаёт SQL напрямую в `sqlite3`. Так проще увидеть, где выполняется запрос и какие гарантии даёт база.

## Путь одного запроса

```mermaid
sequenceDiagram
    participant C as Клиент
    participant A as API
    participant F as Файловое хранилище
    participant D as SQLite
    C->>A: POST /models/1/versions (metadata + artifact)
    A->>A: Проверить metadata и наличие модели
    A->>F: Записать tmp, проверить размер, вычислить SHA256
    F->>F: fsync, rename в UUID.blob, fsync каталога на POSIX
    A->>D: BEGIN IMMEDIATE
    A->>D: MAX(version) + 1; INSERT
    A->>D: COMMIT
    A-->>C: Карточка новой версии
```

Файл загружается полем `artifact`, а метаданные — строкой JSON в поле `metadata`. Это одна multipart-форма. В `/docs` можно заполнить поля и увидеть HTTP-ответ. Способ передачи описан в [документации FastAPI](https://fastapi.tiangolo.com/tutorial/request-forms-and-files/).

В хранилище файл получает серверный UUID. Поэтому название `../../model.pkl`, пришедшее от клиента, не превращается в путь на сервере. Если у модели несколько файлов, клиент заранее упаковывает каталог; сервер хранит архив целиком и не распаковывает его.

Файл и строка БД не участвуют в общей транзакции. При обычной ошибке SQL приложение удаляет свой файл; при аварийном завершении между записью файла и commit может остаться бесхозный файл. Этот компромисс нужно понимать, даже если весь проект небольшой.

## Минимум SQL для чтения кода

`SELECT` читает строки, `INSERT` добавляет, `WHERE` отбирает, а `ORDER BY` задаёт порядок. Здесь `?` — параметр запроса: `sqlite3` получает значение отдельно от SQL-текста.

```python
model_id = 1
rows = connection.execute(
    "SELECT version, artifact_size FROM versions "
    "WHERE model_id = ? ORDER BY version",
    (model_id,),
).fetchall()
```

Запятая в `(model_id,)` создаёт кортеж из одного элемента. Не подставляй пользовательские строки через f-string в SQL: используй параметры, как в примере.

```sql
BEGIN IMMEDIATE;
SELECT COALESCE(MAX(version), 0) + 1 FROM versions WHERE model_id = 1;
-- Далее INSERT с полученным номером в той же транзакции.
COMMIT;
```

`COALESCE(..., 0)` заменяет отсутствие предыдущей версии нулём. `BEGIN IMMEDIATE` получает право записи до вычисления номера, поэтому два запроса не выбирают один и тот же следующий номер одновременно. Уникальный составной ключ дополнительно защищает данные. См. [транзакции SQLite](https://www.sqlite.org/lang_transaction.html).

Внешний ключ `(model_id, version)` у alias проверяет, что выбранная версия принадлежит нужной модели. `UNIQUE(team, name)` запрещает одинаковые имена внутри команды, но разрешает их разным командам.

## Что проверить руками

1. Создай модель; повтори запрос с теми же team/name и получи `409`.
2. Загрузи две версии с разными параметрами и метриками; проверь номера 1 и 2.
3. Назначь `production` версии 1 запросом `PUT` с `{"version": 1}`, затем переназначь на 2.
4. Вызови `GET` alias: вернётся карточка версии 2. Карточка версии 1 по-прежнему доступна.
5. Скачай артефакт; сравни его SHA256 с карточкой версии.
6. Перезапусти сервер с тем же каталогом данных: записи и файлы должны сохраниться.

Не считай заполненные `dataset_ref` и `code_ref` доказательством воспроизводимости. Для реальной воспроизводимости нужны доступные неизменяемые данные, точная ревизия кода, окружение и процедура запуска. В учебном примере эти поля помогают понять, что следует фиксировать.

## Небольшие упражнения

| Упражнение | Как проверить результат |
|---|---|
| Добавить фильтр моделей по точному имени | Тест различает `model` и `model-v2`; существующая фильтрация не ломается |
| Добавить историю назначений aliases | Два переназначения оставляют две записи истории; неуспешное назначение не добавляет запись |
| Сделать клиентскую упаковку каталога в ZIP | Скачать архив и проверить имена и байты файлов внутри без распаковки на сервере |
| Добавить ключ идемпотентности загрузки | Повтор запроса с тем же ключом возвращает ту же версию; другой payload с тем же ключом даёт конфликт |

После каждого изменения запускай тесты из `README.md`. Первое полезное усложнение — одно из упражнений с конкретным критерием проверки, а переход на PostgreSQL или S3 имеет смысл, когда понятны ограничения текущей реализации.
